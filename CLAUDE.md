# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Georgia Tech hackathon project. React (Vite) frontend + FastAPI backend, each with its own `.env` file, backed by a Supabase Postgres project.

```
gtech_hacks/
├── frontend/   # React + Vite app
└── backend/    # FastAPI app
```

## Commands

### Backend (from `backend/`)

```powershell
.\venv\Scripts\Activate.ps1
uvicorn main:app --reload --port 8000
python -m pytest                                          # all tests (config in pytest.ini)
python -m pytest tests/test_billing_rules.py -k code_for  # a subset
```

Tests cover only `billing_rules.py` so far. No linter is configured for the backend.

### Frontend (from `frontend/`)

```powershell
npm run dev       # dev server at http://localhost:5173
npm run build     # production build
npm run lint      # oxlint
npm run preview   # preview a production build
```

No test suite is configured for the frontend yet.

### Running both together

Both dev servers must run concurrently in separate terminals. The frontend calls the backend at `VITE_API_URL` (`frontend/.env`); the backend allows that origin via `FRONTEND_URL` (`backend/.env`) for CORS.

## Environment variables

Neither `.env` file is committed — only `.env.example` is tracked. After pulling changes that add new variables, diff against `.env.example` and add the new keys to your own `.env`.

- `backend/.env`: `FRONTEND_URL` (CORS origin), plus Supabase connection info — `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`. The service role key and DB password are not retrievable via the Supabase MCP server and must be copied from the Supabase dashboard (Settings → API / Settings → Database).
- `frontend/.env`: `VITE_API_URL` (backend base URL), plus `VITE_SUPABASE_URL` + `VITE_SUPABASE_PUBLISHABLE_KEY` for Google sign-in (Supabase Auth) — see "Google sign-in" below. Any variable exposed to the frontend must be prefixed with `VITE_`.
- **Google sign-in has no backend env vars at all.** The Google OAuth Client ID/Secret live only in the Supabase dashboard (Authentication → Sign In / Providers → Google) — Supabase handles the OAuth exchange itself, so our backend never sees or needs those values. The dashboard also needs `http://localhost:5173/**` (or the deployed origin) added under Authentication → URL Configuration → Redirect URLs, or the post-login redirect will be rejected.

A Supabase MCP server is configured in `.mcp.json` (docs/account/database/debugging/development/functions/branching features enabled) for inspecting the project, running SQL, and reading logs/advisors directly from this session.

## Architecture

### Backend

Single-file FastAPI app (`backend/main.py`). CORS is the only configured middleware, restricted to `FRONTEND_URL`.

- `backend/billing_rules.py` is the pure billing logic (no DB/HTTP/Claude), tested in `tests/test_billing_rules.py`: `pick_generic_code`, `ndc_10_to_11` (needs hyphenated input), `code_for` (picks the `drugs.codes` entry by **date of service**; a payer-specific entry beats a general one; overlaps raise), `units` (generic → 1, permanent → dose ÷ billing unit rounded up, via `Decimal`), `dose_for` (mg/kg, mg/m²), `vial_mix` (least waste, then fewest vials), `waste_modifier` (JW/JZ), `admin_codes` (push ≤ 15 min; add-on hour after > 30 min) and `item19`. Rules marked "verify" in the docstrings are our reading of CMS/CPT guidance. Only `ndc_10_to_11` is called so far (by the NDC endpoint); the generic-code pick is still duplicated in JS in `DrugMakerPage.jsx` (orchestration intentionally stays in the browser), so keep the two in sync.

- `GET /api/fda/label/{application_number}` and `GET /api/fda/ndc/{application_number}` proxy openFDA live.
- `GET /api/fda/label-extraction/{application_number}` sends the label's indications/dosage/supply sections to Claude (`claude-opus-5`, JSON-schema structured output) to extract dosing, infusion time, preparation, single-dose vial, approved uses, antineoplastic flag and per-field label-section citations. Needs `ANTHROPIC_API_KEY`; returns 503 without it.
- `GET /api/cms/hcpcs-status/{brand_name}` looks the brand up (case-insensitive exact match on "Drug Name") in the CMS ASP NDC-HCPCS crosswalk and payment limit file checked into `backend/data/` (loaded at startup; quarter in `CMS_QUARTER`). NOC codes (J3490/J3590/J9999…) don't count as permanent. Drugs missing from the crosswalk report "no code found", which can be wrong for drugs CMS doesn't price via ASP. Refresh the files each quarter with `python scripts/update_cms_files.py <crosswalk zip url> <payment limit zip url>`.
- `POST /api/drugs` upserts into the Supabase `drugs` table (PK `application_id`) via the `supabase` Python client using the **service role key** — `drugs` has RLS enabled with no policies, so all DB writes go through the backend, never the frontend. It dumps with `exclude_unset=True`, so omitted fields leave existing column values untouched while explicit `null`s overwrite.
- `GET /api/drugs/search?q=` returns every row (ordered by `brand_name`) when `q` is empty, or an `ilike` brand-name match when it's set. The frontend grid has no search UI and always calls it with no `q`, so in practice this always returns the full seeded set; the `q` filter is left in place for future reuse rather than deleted.
- `GET /api/drugs/profile/{application_id}` returns the full row for one drug (404 if not found) — backs the drug detail page.
- `drugs` columns beyond the original schema: `generic_name`, `approval_date`, `pubchem_query`; `route_of_administration` doubles as the "route" field rather than adding a duplicate column. `has_permanent_code` is the single source of truth for code status (there is no separate `code_status` column), and there is no expected-permanent-code-date column since no data source provides one. The pipeline writes `generic_name` (from the label) but not `approval_date`/`pubchem_query`, which are seed-only. Seeded via `backend/scripts/resolve_drug_data.py` (resolves NDA/route/approval date against openFDA, writes `backend/scripts/drug_seed_data.json`) and `backend/scripts/seed_drugs.py` (loads that JSON and upserts on `application_id`, so pipeline-added drugs and pipeline-filled columns survive a re-seed) — both re-runnable, network-free after the JSON snapshot exists.
- `GET /api/npi/{number}` proxies the free, live NPPES NPI Registry (`npiregistry.cms.hhs.gov`) and returns name, specialty, state, and a Medicare Part B contractor looked up from `MEDICARE_CONTRACTOR_BY_STATE` — a hand-typed partial map (not all 50 states yet; unmapped states return a "verify with CMS" placeholder instead of a guess).
- `POST /api/practices` upserts into the `practices` table **on `email`** (not `npi` — email is the durable identity now that Google sign-in exists; `npi` stays `UNIQUE` too but is captured once at sign-up, not used to dedupe repeat sign-ins). `GET /api/practices/by-npi/{npi}` and `GET /api/practices/by-email/{email}` each fetch one back (404 if not found). `practices` columns: `npi`, `email` (nullable at the column level only because it was added after one pre-existing test row without it — every row written through the current flow always has one), `name`, `specialty`, `state`, `medicare_contractor`, `capabilities` (jsonb, e.g. `{infusion_chairs, refrigeration}`), `payers` (jsonb array of payer names — a flat list, not a `payers` reference table, since there's no other payer-specific logic yet to justify the join), `shares_signals` (default `false`, the pharma opt-in that `pharma_summary` filters on). RLS is enabled with no policies, same pattern as `drugs`.
- `GET /api/pins`, `PUT /api/pins/{application_id}` and `DELETE /api/pins/{application_id}` manage a practice's pinned drugs (`pinned_drugs` table, PK `(practice_id, application_id)`, both FKs cascade). Unlike the email-in-the-URL practice endpoints, these use the `current_practice` dependency: the frontend sends the Supabase session's access token as `Authorization: Bearer …`, the backend verifies it with `supabase.auth.get_user(token)` and looks the practice up by the verified email (401 bad/missing token, 404 no practice row). PUT/DELETE are idempotent on purpose (no toggle endpoint). Reuse `current_practice` for any new per-user endpoint.
- The full `Comp_Details/BuildPlan.md` §5 schema exists in Supabase (8 tables + 1 view), all RLS-on/no-policies so only the backend's service role touches them; column meanings and JSON shapes are in Postgres `COMMENT`s. Beyond the original columns, `drugs` has `typical_adult_dose` (jsonb `{amount, unit}` — a fixed dose when the label gives one, else a `mg/kg` / `mg/m2` rate for `billing_rules.dose_for`; cost per dose is skipped for rates since the unit won't match the billing unit), `is_antineoplastic`, and the JSON lists `codes` (effective-dated, drives Switch), `payer_policies` and `distributors`; the existing `ndcs` column doubles as the plan's "packages" list. New tables: `practice_drugs` (unique per practice+drug; status `considering|holding|adopting|active`, lights, hold list/invoices/stock as JSON), `patients`, `treatments` (order → nurse record → claim in one row; status `ordered|signed|administered|claim_ready|exported|needs_recoding`), `tasks` (the team board; FK to `practice_drugs`, optional FK to `treatments`; `kind` is a machine tag so code can find and auto-complete cards), `events` (activity log with region/specialty snapshots and a groupable `reason`), and `help_requests` (status `open|assigned|resolved`). The `pharma_summary` view (security invoker) is the privacy boundary: opted-in practices only, grouping sets by drug × event type × reason, overall / per region / per specialty, and counts nulled when a cell has < 5 distinct practices. The pipeline writes `typical_adult_dose` and `is_antineoplastic` (from Claude's extraction) and `ndcs[].ndc_11` (the NDC endpoint converts each package via `billing_rules.ndc_10_to_11`, `null` if malformed); it doesn't write `codes`, `payer_policies`, `distributors` or `ndcs[].strength_mg` yet, and `PracticeRecord` doesn't write `shares_signals`.
- **Phase 3 (Prepare) endpoints — all added to `backend/main.py`:**
  - `POST /api/practice-drugs/{practice_drug_id}/team-ready` — **idempotent**: if the practice_drug already has tasks, returns them without inserting again. Otherwise sets `practice_drugs.status='adopting'` and inserts exactly four `tasks` rows (stage=`prepare`). Instruction text built from the drug's own row.
  - `GET /api/practice-drugs/{practice_drug_id}/tasks` — returns `{drug_name, drug: {brand_name, codes, approval_date, storage_requirements}, practice_drug: {id, status, planned_patients_per_month, hold_list_count, stock_on_hand, ready_at}, tasks[]}`. One call gives the workspace page everything it needs.
  - `PATCH /api/tasks/{task_id}` — unified update: accepts `{status?, inputs?}`. Inputs are merged non-destructively (existing keys survive). After saving, runs `_recalculate_readiness`: if all tasks done **and** `stock_on_hand` total qty > 0 → sets `practice_drugs.status='active'` + `ready_at=now()`; if a task is un-done and status was active → reverts to `adopting`. Returns updated task row.
  - `PATCH /api/tasks/{task_id}/status` — backward-compat alias for the above, kept so old callers don't break.
  - `GET /api/practices/{email}/workspaces` — returns every `practice_drugs` row for the practice that has ≥ 1 task, each with `{practice_drug_id, application_id, status, brand_name, tasks_done, tasks_total}`. Used by the View Tasks toggle on `/doctor/drugs`.
  - `GET /api/workspaces/by-role/{role}` — unauthenticated, cross-practice: every `practice_drugs` row (across all practices) with ≥ 1 task for the given `role` (`front_desk`/`nurse`/`biller`; 400 on anything else), each with `{practice_drug_id, application_id, status, brand_name, practice_name, tasks_done, tasks_total}` — `tasks_done`/`tasks_total` count only that role's tasks. Backs the Nurse/Biller tabs on `/doctor/drugs`, which have no login of their own.
  - **Database columns:** `tasks.inputs` (jsonb, NOT NULL DEFAULT `{}`) — holds each card's structured entries (order placed, supplies confirmed, insurers reviewed…) — and `practice_drugs.ready_at` (timestamptz, nullable) — set when workspace reaches "Ready to treat". Both were added directly via the Supabase MCP (`apply_migration`); there is no migration file checked in.
  - **Demo drug BLA761508 (Pasatru)** seeded with: `distributors` (ASD Healthcare, McKesson Specialty Health), `codes` (J3590 generic from 2026-02-01, J0289 permanent from 2026-10-01), `payer_policies` (Medicare/BCBS/Aetna), `ndcs[].strength_mg=100` and `ndcs[].single_dose=true`.

### Frontend

- `main.jsx` wraps `App` in `BrowserRouter` — routing is React Router (`react-router-dom`), route table lives in `App.jsx`.
- `App.jsx` renders `ShaderBackground` once, outside `<Routes>`, so a single fixed full-viewport Three.js canvas (`position: fixed`, `z-index: -1`) persists as a global background behind every page rather than being re-mounted per route.
- Pages live in `src/pages/` and are matched 1:1 to entries in `App.jsx`'s route table. `/temp/*` routes (e.g. `/temp/drug-search`) mark pages that are scaffolding/in-progress rather than final navigation. `/drugs/:applicationId` (`DrugDetailPage.jsx`) is currently a placeholder destination for drug search cards — the real "Considering" detail view for a specific drug is a separate, not-yet-built task.
- `Home.jsx` (`/`) is the top-level role picker — "Drug maker", "Doctor" (→ `/doctor`, Google-gated), and now "Nurse"/"Biller"/"Front Desk" (→ `/staff/nurse`, `/staff/biller`, `/staff/front_desk`), all plain `Button`s with no auth of their own for the staff roles.
- `/staff/:role` (`StaffWorkspacesPage.jsx`) is the unauthenticated staff entry point: it renders `DrugSearchGrid` with `view={role}` (no `email`), which fetches `GET /api/workspaces/by-role/{role}` — every workspace across **every** practice that has a task for that role, not just one practice's. An unrecognized `:role` redirects to `/`. Reuses the exact same `WorkspaceCard` grid as the doctor's own "View Tasks" tab; clicking a card goes to the same `/doctor/workspace/:practiceDrugId` page a doctor would use, which has no auth gate of its own and is fully editable — so nothing stops a nurse from checking off a biller's task today. Edit-scoping staff to their own role's tasks is unimplemented (future work, not a current restriction).
- `/doctor` (`DoctorChoicePage.jsx`) is a landing page with three choices — "View Drugs" (`/doctor/drugs`, `DoctorPage.jsx`, the search grid), "Sign Up" (`/sign-up`, `SignUpPage.jsx`), or "Sign In" (Google, no form). Real identity is Google sign-in via **Supabase Auth** (`src/lib/supabaseClient.js` — a client built from `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY`, used *only* for auth; all app data still goes through the FastAPI backend, never straight to Supabase from the frontend). Both "Sign Up" and "Sign In" call `supabase.auth.signInWithOAuth({ provider: 'google' })`, redirecting to Google and back to `/auth/callback` (`AuthCallbackPage.jsx`), which reads the verified session and branches:
  - **From Sign Up:** `SignUpPage.jsx` collects the NPI lookup (`GET /api/npi/{number}`) + a capabilities/payers checklist *before* redirecting to Google, stashing that in-progress data via `src/lib/pendingSignUp.js` (`sessionStorage`, since it has to survive the full-page redirect to Google and back — `localStorage` would be wrong here, this is scoped to one attempt). The callback page reads it back, adds the now-verified email, and `POST /api/practices` for the first time.
  - **From Sign In:** the callback page has no pending data, so it calls `GET /api/practices/by-email/{email}` directly — found → logged in; not found → sent to `/sign-up`, where `SignUpPage.jsx` detects the already-verified session (`supabase.auth.getSession()`) and skips a second Google redirect, going straight to "Finish sign up" once the NPI form is filled in.
  - Either way, the resulting practice row is cached in `src/lib/practiceSession.js` (a `localStorage` wrapper) for other pages to read for personalization — not read by any other page yet.
- Feature UI lives in `src/components/<Feature>/`, colocating the component, its CSS Module, and any mock data (e.g. `DrugSearch/DrugSearch.jsx` + `DrugSearch.module.css` + `mockTherapies.js`). Components in this layer are written route-agnostic — they take data/callbacks as props (e.g. `therapies`, `onSelectTherapy`) rather than reaching into routing or fetching themselves — so pages own data-fetching/wiring and components stay reusable.
- Styling is CSS Modules by default (`*.module.css`, imported as `styles` and referenced via `styles.foo`), not a CSS framework or global stylesheet beyond `index.css`. **Exception:** `src/components/DoctorDashboard/` uses Tailwind CSS instead — `src/tailwind.css` imports only `theme.css` + `utilities.css` (no Preflight), scoped intentionally so it doesn't reset native form/button styling on the rest of the app's plain-CSS pages. Any component using Tailwind classes there imports that file directly. Because Preflight is skipped, native form controls (`<input>`, `<button>`) need explicit `appearance-none border-0 bg-transparent` etc. themselves — nothing resets them for free.
- `DoctorDashboard`'s `DrugSearchGrid.jsx` debounces (300ms) against the live `GET /api/drugs/search?q=` backend endpoint (Enter also searches immediately); `DrugCard.jsx` renders each result as a `react-router-dom` `Link` to `/drugs/:applicationId`, with border/accent color (amber = unclassified generic billing code, green = permanent HCPCS code) derived from `has_permanent_code`/`generic_billing_code`/`permanent_hcpcs_code` on the row. Sibling-dimming on hover is a plain CSS rule (`.drug-grid:hover .drug-card:not(:hover)`) in `tailwind.css`, not React state. The grid also fetches the practice's pins (`src/api/pins.js`, which attaches the session token) alongside the drugs and lists pinned cards first, each group alphabetical; pin clicks are optimistic and revert on failure, and if pins can't load (e.g. signed in without a practice row) the pin buttons are hidden. The pin button is a *sibling* of the card's `Link`, not a child (no `<button>` inside `<a>`), so the hover lift/scale and the `drug-card` class live on a wrapper `div`. `ConsideringDashboard.tsx` (search-then-bento-grid mock) is currently unused/orphaned pending that detail-page work — not deleted since it may be reused.
- **`/doctor/drugs` (`DoctorPage.jsx`) has a two-button toggle** above the grid — "View Drugs" (the existing drug card grid, unchanged) and "View Tasks" (workspace rectangles for the signed-in practice). The toggle state lives in `DoctorPage`; `DrugSearchGrid` accepts `view` (`'drugs'|'tasks'`, plus the staff role views `'nurse'|'biller'|'front_desk'` used by `StaffWorkspacesPage` — see above) and `email` props. The workspace fetch is lazy and keyed by `view`, so switching views re-fetches only the first time that view is activated. An empty workspace list shows a plain-text message ("No workspaces yet — adopt a drug to create one"). Clicking a workspace rectangle navigates to `/doctor/workspace/:practiceDrugId`. The whole page is gated behind sign-in (anonymous visitors bounce to `/doctor`) — this is unrelated to and unchanged by the staff roles, which live at `/staff/:role` instead.
- `/doctor/workspace/:practiceDrugId` (`TeamWorkspacePage.jsx`) is the Phase 3 team workspace page. It fetches tasks via `GET /api/practice-drugs/{id}/tasks`, groups them by role (front desk → nurse → biller), and renders each with its instruction text and a checkbox bound to `status` ('todo' ↔ 'done'). Checkbox toggles write back to the tasks table via `PATCH /api/tasks/{id}/status` with an optimistic update and rollback on failure. Plain document style matches `DrugProfileDashboard` — no colored dots, no card borders.
- `DrugSearch` (a different, older component under `src/components/DrugSearch/`) still runs against local mock data (`mockTherapies.js`); it has not been wired to the backend.
- Styling is CSS Modules throughout (`*.module.css`, imported as `styles` and referenced via `styles.foo`), not a CSS framework or global stylesheet beyond `index.css`.
- Backend calls live in `src/api/` (e.g. `drugMaker.js`), using `VITE_API_URL`. `DrugMakerPage` calls the four FDA/CMS endpoints in parallel from the two `DrugMaker` inputs (application ID → FDA, drug name → CMS), maps each response to `drugs` columns (empty values → `null`), then `POST`s to `/api/drugs`. It skips the save if both the label and NDC calls fail, and omits columns from any call that failed. When two sources map the same column (e.g. `route_of_administration` from label, falling back to NDC), the earlier source in `SOURCES` wins unless its value is null; `citations` is instead concatenated across sources. `deriveColumns` then computes the cross-source columns: `generic_billing_code` (null when a permanent code exists, else J9999 cancer / J3590 BLA / J3490) and `cost_per_dose` (CMS payment limit × Claude's typical adult dose; only possible once a drug has a permanent code).
- `DrugSearch` currently runs against local mock data (`mockTherapies.js`); it has not yet been wired to the FastAPI/Supabase backend.
- Linting is `oxlint`, not ESLint — config in `.oxlintrc.json` enables the `react` and `oxc` plugins with `react/rules-of-hooks` as an error.
