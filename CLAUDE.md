# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Georgia Tech hackathon project. React (Vite) frontend + FastAPI backend, each with its own `.env` file, backed by a Supabase Postgres project.

```
gtech_hacks/
├── frontend/   # React + Vite app
└── backend/    # FastAPI app
```

## Commands

### Backend (from `backend/`)

```powershell
.\venv\Scripts\Activate.ps1
uvicorn main:app --reload --port 8000
python -m pytest                                          # all tests (config in pytest.ini)
python -m pytest tests/test_billing_rules.py -k code_for  # a subset
python scripts/reset_demo.py <practice email>             # reset the Treat & Bill demo (see below)
```

Tests cover `billing_rules.py` (`tests/test_billing_rules.py`) and the claim builder (`tests/test_claims.py`, built on the Pasatru demo data and demo patients). Neither touches the database: `treat_and_bill.claims.build_claim` is pure, with `refresh_claim` doing the lookups, and `tests/conftest.py` supplies placeholder Supabase settings so the modules import without a `.env`. No linter is configured for the backend.

### Frontend (from `frontend/`)

```powershell
npm run dev       # dev server at http://localhost:5173
npm run build     # production build
npm run lint      # oxlint
npm run preview   # preview a production build
```

No test suite is configured for the frontend yet.

### Running both together

Both dev servers must run concurrently in separate terminals. The frontend calls the backend at `VITE_API_URL` (`frontend/.env`); the backend allows that origin via `FRONTEND_URL` (`backend/.env`) for CORS.

## Environment variables

Neither `.env` file is committed — only `.env.example` is tracked. After pulling changes that add new variables, diff against `.env.example` and add the new keys to your own `.env`.

- `backend/.env`: `FRONTEND_URL` (CORS origin), plus Supabase connection info — `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`. The service role key and DB password are not retrievable via the Supabase MCP server and must be copied from the Supabase dashboard (Settings → API / Settings → Database).
- `frontend/.env`: `VITE_API_URL` (backend base URL), plus `VITE_SUPABASE_URL` + `VITE_SUPABASE_PUBLISHABLE_KEY` for Google sign-in (Supabase Auth) — see "Google sign-in" below. Any variable exposed to the frontend must be prefixed with `VITE_`.
- **Google sign-in has no backend env vars at all.** The Google OAuth Client ID/Secret live only in the Supabase dashboard (Authentication → Sign In / Providers → Google) — Supabase handles the OAuth exchange itself, so our backend never sees or needs those values. The dashboard also needs `http://localhost:5173/**` (or the deployed origin) added under Authentication → URL Configuration → Redirect URLs, or the post-login redirect will be rejected.

A Supabase MCP server is configured in `.mcp.json` (docs/account/database/debugging/development/functions/branching features enabled) for inspecting the project, running SQL, and reading logs/advisors directly from this session.

## Architecture

### Backend

FastAPI app split into one folder per product stage. `backend/main.py` only creates the app, adds CORS (the only middleware, restricted to `FRONTEND_URL`) and includes each module's `APIRouter`, **in the order the routes were originally defined** (FastAPI matches routes in registration order, so keep new routers in a sensible place in that list). Run everything from `backend/` (`uvicorn main:app`, `pytest`); imports are absolute from there (`from core.db import supabase`).

Shared helpers have no leading underscore; helpers used only inside one file keep it.

- `backend/billing_rules.py` is the pure billing logic (no DB/HTTP/Claude), tested in `tests/test_billing_rules.py`: `pick_generic_code`, `ndc_10_to_11` (needs hyphenated input), `code_for` (picks the `drugs.codes` entry by **date of service**; a payer-specific entry beats a general one; overlaps raise), `units` (generic → 1, permanent → dose ÷ billing unit rounded up, via `Decimal`), `dose_for` (mg/kg, mg/m²), `vial_mix` (least waste, then fewest vials), `waste_modifier` (JW/JZ), `admin_codes` (push ≤ 15 min; add-on hour after > 30 min) and `item19`. Rules marked "verify" in the docstrings are our reading of CMS/CPT guidance. Only `ndc_10_to_11` is called so far (by the NDC endpoint); the generic-code pick is still duplicated in JS in `DrugMakerPage.jsx` (orchestration intentionally stays in the browser), so keep the two in sync.

- `GET /api/fda/label/{application_number}` and `GET /api/fda/ndc/{application_number}` proxy openFDA live.
- `GET /api/fda/label-extraction/{application_number}` sends the label's indications/dosage/supply sections to Claude (`claude-opus-5`, JSON-schema structured output) to extract dosing, infusion time, preparation, single-dose vial, approved uses, antineoplastic flag and per-field label-section citations. Needs `ANTHROPIC_API_KEY`; returns 503 without it.
- `GET /api/cms/hcpcs-status/{brand_name}` looks the brand up (case-insensitive exact match on "Drug Name") in the CMS ASP NDC-HCPCS crosswalk and payment limit file checked into `backend/data/` (loaded at startup; quarter in `CMS_QUARTER`). NOC codes (J3490/J3590/J9999…) don't count as permanent. Drugs missing from the crosswalk report "no code found", which can be wrong for drugs CMS doesn't price via ASP. Refresh the files each quarter with `python scripts/update_cms_files.py <crosswalk zip url> <payment limit zip url>`.
- `POST /api/drugs` upserts into the Supabase `drugs` table (PK `application_id`) via the `supabase` Python client using the **service role key** — `drugs` has RLS enabled with no policies, so all DB writes go through the backend, never the frontend. It dumps with `exclude_unset=True`, so omitted fields leave existing column values untouched while explicit `null`s overwrite.
- `GET /api/drugs/search?q=` returns every row (ordered by `brand_name`) when `q` is empty, or an `ilike` brand-name match when it's set. The frontend grid has no search UI and always calls it with no `q`, so in practice this always returns the full seeded set; the `q` filter is left in place for future reuse rather than deleted.
- `GET /api/drugs/profile/{application_id}` returns the full row for one drug (404 if not found) — backs the drug detail page.
- `drugs` columns beyond the original schema: `generic_name`, `approval_date`, `pubchem_query`; `route_of_administration` doubles as the "route" field rather than adding a duplicate column. `has_permanent_code` is the single source of truth for code status (there is no separate `code_status` column), and there is no expected-permanent-code-date column: the drug maker's launch details put the expected code and its date into the dated `codes` list instead. The pipeline writes `generic_name` (from the label) but not `approval_date`/`pubchem_query`, which are seed-only. Seeded via `backend/scripts/resolve_drug_data.py` (resolves NDA/route/approval date against openFDA, writes `backend/scripts/drug_seed_data.json`) and `backend/scripts/seed_drugs.py` (loads that JSON and upserts on `application_id`, so pipeline-added drugs and pipeline-filled columns survive a re-seed) — both re-runnable, network-free after the JSON snapshot exists.
- `GET /api/npi/{number}` proxies the free, live NPPES NPI Registry (`npiregistry.cms.hhs.gov`) and returns name, specialty, state, and a Medicare Part B contractor looked up from `MEDICARE_CONTRACTOR_BY_STATE` — a hand-typed partial map (not all 50 states yet; unmapped states return a "verify with CMS" placeholder instead of a guess).
- `POST /api/practices` upserts into the `practices` table **on `email`** (not `npi` — email is the durable identity now that Google sign-in exists; `npi` stays `UNIQUE` too but is captured once at sign-up, not used to dedupe repeat sign-ins). `GET /api/practices/by-npi/{npi}` and `GET /api/practices/by-email/{email}` each fetch one back (404 if not found). `practices` columns: `npi`, `email` (nullable at the column level only because it was added after one pre-existing test row without it — every row written through the current flow always has one), `name`, `specialty`, `state`, `medicare_contractor`, `capabilities` (jsonb, e.g. `{infusion_chairs, refrigeration}`), `payers` (jsonb array of payer names — a flat list, not a `payers` reference table, since there's no other payer-specific logic yet to justify the join), `shares_signals` (default `false`, the pharma opt-in that `pharma_summary` filters on). RLS is enabled with no policies, same pattern as `drugs`.
- `GET /api/pins`, `PUT /api/pins/{application_id}` and `DELETE /api/pins/{application_id}` manage a practice's pinned drugs (`pinned_drugs` table, PK `(practice_id, application_id)`, both FKs cascade). Unlike the email-in-the-URL practice endpoints, these use the `current_practice` dependency: the frontend sends the Supabase session's access token as `Authorization: Bearer …`, the backend verifies it with `supabase.auth.get_user(token)` and looks the practice up by the verified email (401 bad/missing token, 404 no practice row). PUT/DELETE are idempotent on purpose (no toggle endpoint). Reuse `current_practice` for any new per-user endpoint.
- The full `Comp_Details/BuildPlan.md` §5 schema exists in Supabase (8 tables + 1 view, plus `notifications` from `backend/migrations/002_notifications.sql`), all RLS-on/no-policies so only the backend's service role touches them; column meanings and JSON shapes are in Postgres `COMMENT`s. Beyond the original columns, `drugs` has `typical_adult_dose` (jsonb `{amount, unit}` — a fixed dose when the label gives one, else a `mg/kg` / `mg/m2` rate for `billing_rules.dose_for`; cost per dose is skipped for rates since the unit won't match the billing unit), `is_antineoplastic`, and the JSON lists `codes` (effective-dated, drives Switch), `payer_policies` and `distributors`; the existing `ndcs` column doubles as the plan's "packages" list. New tables: `practice_drugs` (unique per practice+drug; status `considering|holding|adopting|active`, lights, hold list/invoices/stock as JSON), `patients`, `treatments` (order → nurse record → claim in one row; status `ordered|signed|administered|claim_ready|exported|needs_recoding`), `tasks` (the team board; FK to `practice_drugs`, optional FK to `treatments`; `kind` is a machine tag so code can find and auto-complete cards), `events` (activity log with region/specialty snapshots and a groupable `reason`), and `help_requests` (status `open|assigned|resolved`). The `pharma_summary` view (security invoker) is the privacy boundary: opted-in practices only, grouping sets by drug × event type × reason, overall / per region / per specialty, and counts nulled when a cell has < 5 distinct practices. The pipeline writes `typical_adult_dose` and `is_antineoplastic` (from Claude's extraction) and `ndcs[].ndc_11` (the NDC endpoint converts each package via `billing_rules.ndc_10_to_11`, `null` if malformed); the NDC endpoint also parses `ndcs[].strength_mg` (`billing_rules.vial_strength_mg`: openFDA's single active-ingredient strength × the vial volume in the package description, e.g. "300 mg/5mL" → 300; "150 mg/1" powders → per vial; `null` when unreadable) and `ndcs[].single_dose` (`is_single_dose_package`). `codes`, `payer_policies`, `distributors` and `ndcs[].list_price` come from the drug maker's launch details (below). `PracticeRecord` doesn't write `shares_signals`. Pasatru's demo data uses openFDA's real 300 mg / 5 mL vial (`DEMO_DRUG`, `seed_patients.py`); `tests/test_claims.py` keeps its own fixed example data (100 mg vials, J0289 as a stand-in code).
- **Treat & Bill — patients:** `GET /api/patients`, `GET /api/patients/{id}` and `PATCH /api/patients/{id}/note` (`{note}`; `{visit_note}` also accepted) all use `current_practice` and only ever touch the signed-in practice's rows (another practice's id 404s). Responses add display aliases `name`, `dob`, `insurance` (what `PatientChartPage` reads) on top of the columns.
- **Treat & Bill — orders:** API responses follow the field names the Track B pages read (`src/api/patients.js`, `treatments.js`), not the column names; `treatment_view` (in `treat_and_bill/shared.py`) does the mapping. `POST /api/treatments` (`current_practice`; `{patient_id, practice_drug_id | application_id, dose?}`) calculates the dose (`dose_for` from `typical_adult_dose` × weight, or the doctor's override in mg) and least-waste vials (`vial_mix` over `ndcs[].strength_mg`), stores `vial_mix` as `[{ndc_11, strength, count}]`, returns `dose: {amount, unit}` + `vial_mix: {vials, vial_size_mg, total_mg, waste_mg, packages}`, and creates the doctor's `order_sign` card. `POST /api/treatments/{id}/sign` (409 unless `ordered`) freezes the note into `signed_note`, completes `order_sign`, and creates the patient's chain (`stage='treat_and_bill'`): `prior_auth` (biller; only if the patient's payer policy has `prior_auth: true`), `buy_for_patient` (front desk; only if `stock_on_hand` < vials needed), then `prep_dose` → `give_infusion` (nurse) → `claim_review` (biller), each `waits_on` the step before. `PATCH /api/tasks/{id}` won't change the status of `order_sign`/`prep_dose`/`give_infusion`/`claim_review` (409 — their pages complete them) and won't complete `prior_auth` without `inputs.auth_number` (422). `GET …/tasks` adds `patient_id`/`patient_name` on per-patient cards. `GET /api/practice-drugs/{id}/treatments` (no login, like the board) is the Patients-tab tracker: one row per dose with `dose_number` and `steps[{task_id, kind, title, role, state: done|waiting|todo, waiting_on}]`.
- **Treat & Bill — documentation check:** `POST /api/treatments/{id}/doc-check` (`current_practice`) returns `{checks: [{id, label, passed, quote}], draft_text, prior_auth_required, checked_at}` (what `PatientChartPage` reads). Code builds the requirement list (`_doc_requirements`: diagnosis from `approved_uses_and_conditions`, plus prior therapy / required test when there's a single approved use, weight for `mg/kg` dosing or height+weight for `mg/m2`, and each entry in the patient's payer policy `documentation_requirements`); Claude (`claude-opus-5`, effort `low`, JSON-schema output, `fallbacks: "default"`) only judges the note against it and quotes it. A pass only stands if the quote is verbatim in the note and neither it nor its note line has an unfilled `[placeholder]` (then `draft_text` asks for the blanks to be filled). Stored in `treatments.documentation_check` (`items[{id, requirement, passed, quote}]`, which claim check 6 reads, plus a cache `key` over note + requirements so an unchanged note skips Claude, and `note_sha256`). After signing it returns the stored result instead of re-running. `POST …/sign` 409s unless the check was run on the current note (gaps don't block signing — the doctor decides; claim check 6 flags them). Needs `ANTHROPIC_API_KEY` (503 without). Pasatru's BCBS policy has `documentation_requirements: ["Genetic confirmation of an ACVR1 mutation (e.g. R206H)"]`.
- **Treat & Bill — nurse record** (no login, by treatment id, like the rest of `/staff/*`; shapes follow `TreatmentRecordPage.jsx`): `GET /api/treatments/{id}` returns the `treatment_view` with `preparation {vials_used, lot_number, waste_mg, dose_given, jw_jz, packages}` and `administration {date_of_service, start_time, stop_time, duration_minutes, admin_codes: ["96365", "96366 × 2"], admin_code_lines}`, each `null` until saved. `PATCH …/preparation` (`{vials_used, lot_number, waste_mg}`, blanks default to the order's plan) stores `vials_used` as `[{ndc_11, lot, quantity}]`, sets `dose_given` = mg drawn − waste, takes the vials out of `practice_drugs.stock_on_hand` (a re-save puts the previous vials back first; never below zero) and completes `prep_dose`; it 409s while `prep_dose` is still waiting (prior auth / buy-for-patient). `PATCH …/administration` (`{date_of_service, start_time: "HH:MM", stop_time}`, wall-clock times stored without zone conversion) needs the preparation saved first, sets status `administered` and completes `give_infusion`. Both 409 on an unsigned order or an exported claim, and can be re-saved until export. JW/JZ and admin codes come from `billing_rules.waste_modifier` / `admin_codes` (chemo codes when `is_antineoplastic`).
- **Treat & Bill — claim** (no login; shape follows `ClaimPage.jsx`): `_build_claim` assembles the CMS-1500 from the treatment — code by **date of service** and payer (`code_for`, so a DOS on/after a permanent code's `from` switches automatically), `units`, JW line / JZ modifier, `item19` (generic codes only; cost = invoice `cost_per_vial` × vials), admin lines, Box 21 from the ICD-10 prefix of `patients.diagnosis`, Box 23 from the `prior_auth` card's `inputs.auth_number`, 24F charges (invoice cost split used/waste; admin lines from `DEMO_ADMIN_FEES`, labeled demo) — plus the 8 checks `[{id: item19|ndc|units|waste_modifier|diagnosis|documentation|admin_code|attachments, label, passed, message, fix_field}]` (`fix_field` is the claim page's element id to scroll to). The invoice price comes from `practice_drugs.invoices[].lines[]`, so without an invoice checks 1/2/8 fail; check 6 reads `treatments.documentation_check.items`. Saving the administration (or re-saving the preparation afterwards) rebuilds it and sets status `claim_ready`; `GET /api/treatments/{id}/claim` rebuilds on every view until export (409 before the infusion is recorded) and stores `claim`, `claim_checks`, `billing_code`. `POST …/export` 409s listing failing checks, else freezes the claim (`exported_at`), sets `exported` and completes `claim_review`; exporting again returns the frozen claim. `python scripts/seed_patients.py <practice email>` resets that practice's demo patients (deleting cascades to their treatments), all written for Pasatru's 300 mg vials: Maria/Medicare (68 kg → 3 vials, 220 mg waste → JW; Medicare through disability), James/BCBS (82 kg, note missing the ACVR1 genetic confirmation), Aisha/Aetna (60 kg → exactly 2 vials → JZ), Daniel/UnitedHealthcare (75 kg; no Pasatru policy on file — the hold-list patient).
- **Drug maker launch details:** `POST /api/drugs` also takes an optional `launch` object (not a column): `{approval_date, list_price_per_vial, distributors: [names], expected_code: {code, type: permanent|temporary, unit, effective_from}, coverage: [{payer, covered, prior_auth, notes, documentation_requirements}]}` (`covered`/`prior_auth` null = under review). `launch_columns` (in `drug_engine/drugs.py`, pure) turns it into `codes` (the generic code from the approval date to the day before `effective_from`, then the expected code; 422 when the dates overlap), `distributors` `[{name}]`, `payer_policies`, and `list_price` on every non-sample `ndcs` entry. A save with `launch` sends every practice a `launch_message` notification (dedupe `launch:{application_id}`, so re-saving doesn't repeat it).
- **Consider — lights** (`consider/lights.py`, `compute_lights(drug, practice, practice_drug)`): **coverage** checks each of `practices.payers` against `drugs.payer_policies` (covered → green; prior auth or under review or no policy on file → yellow, "verify"; not covered → red; the light takes the worst; gray with no payers). **Payment timing** is a labeled estimate, timing only (no profit claims): one typical dose's up-front cost (`typical_adult_dose` at a 70 kg / 1.8 m² reference adult → `vial_mix` → vial prices, the practice's invoice `cost_per_vial` winning over the launch `list_price`; falls back to `cost_per_dose`), an assumed wait of ~2 months under a generic code or ~1 month under a product-specific one, and with `planned_patients_per_month` set, cost × patients × months paid out before payments start. Yellow under a generic code, green under its own code. `POST /api/practice-drugs/considering` reads the existing row first so the estimate uses the plan and invoices.
- **Consider — decisions** (`consider/decisions.py`, `current_practice`; another practice's workspace or patient 404s): `PATCH /api/practice-drugs/{id}/plan` (`{planned_patients_per_month}` 0–1000 or null) saves it and returns the row with recomputed `lights`. `GET/POST /api/practice-drugs/{id}/hold-list` (`{patient_id, note?}`; adding someone already held updates the note) and `DELETE …/hold-list/{patient_id}` return `{status, hold_list: [{patient_id, added_at, note, name, payer}]}`. The first patient held moves `considering` → `holding`; emptying the list moves `holding` back to `considering` (later statuses are left alone).
- **Notifications (the bell):** `notifications` table (`practice_id`, `role` default `doctor`, `kind`, `title`, `body`, `link` = app route, optional `application_id`/`treatment_id` FKs, unique `(practice_id, dedupe_key)`, `read_at`). Endpoints (`current_practice`): `GET /api/notifications?role=doctor` → `{notifications (newest first, max 30), unread_count}`, `POST /api/notifications/{id}/read`, `POST /api/notifications/read-all`. Kinds and triggers: `launch_message` (drug maker launch), `code_change_upcoming` (≤ 30 days before a change in `codes`) and `code_changed` (for 60 days after, mentioning the hold list), both created by `switch.code_changes.notify_code_changes` each time the bell loads since there's no scheduler; `prior_auth_needed` (signing an order whose payer needs prior auth; still the doctor's bell, since staff pages have no login); `ready_to_treat` (`workspace/tasks._recalculate_readiness` when a workspace turns active, once). All go to the doctor for now.
- **Demo reset:** `python scripts/reset_demo.py <practice email> [--received] [--all-workspaces]` — run before each rehearsal. Sets the practice's payers (Medicare/BCBS/Aetna/UnitedHealthcare) and capabilities, re-applies Pasatru's demo data from `DEMO_DRUG` in the script (codes, payer policies, distributors, `ndcs` with `strength_mg`, dose — the source of truth if the drug-maker pipeline ever overwrites them), deletes the practice's Pasatru workspace (cascading to tasks/treatments; `--all-workspaces` deletes every workspace of the practice), reseeds the patients, and clears the practice's notifications (so a live Pasatru launch sends its message again; `DEMO_DRUG` also sets the vial `list_price` of $1,850 for the payment estimate). `--received` pre-creates the Pasatru workspace with a $1,850/vial invoice and 4 vials in stock (Maria's 3, so James's order gets a Buy card), for when the Receiving card can't record an invoice. Verified end to end: from a reset, considering → team-ready → setup done → active → Maria order/doc-check/sign/prep/infusion → claim with all 8 checks → export works entirely through the API.
- **Phase 3 (Prepare) endpoints — in `backend/workspace/` (`setup.py`, `tasks.py`):**
  - `POST /api/practice-drugs/{practice_drug_id}/team-ready` — **idempotent**: if the practice_drug already has tasks, returns them without inserting again. Otherwise sets `practice_drugs.status='adopting'` and inserts the six setup tasks from `Comp_Details/DataContract.md` §3 (stage=`prepare`): `plan_patients` (doctor, "Set planned patients"), `purchasing` ("Place the order"), `receiving` ("Receive & store"), `nurse_setup`, `payer_review` (biller, "Review insurers": the practice's `payers` × the drug's `payer_policies`), `billing_setup` ("Confirm billing setup", incl. the permanent code's effective date). If planned patients was already set on the drug page (`PATCH …/plan`, `consider/decisions.py`), `plan_patients` is created already done. Waits: purchasing → plan_patients, receiving → purchasing, billing_setup → receiving (Review insurers deliberately doesn't gate Confirm billing setup — both only gate Ready). Instruction text is templated from the drug's row; live numbers (order quantity, Item 19 example) are for the planned `purchasing-plan` / `billing-setup` endpoints (`WorkspacePlan.md` Layers 3/6). Workspaces created before this keep their original 4 tasks.
  - `PATCH /api/practice-drugs/{id}` (`{planned_patients_per_month}`; no login, like the board) — the doctor's number, saved on `practice_drugs` (its real home). A value > 0 completes the `plan_patients` card; clearing it to 0 is refused (409) once another task waits on that card (see "No reopening" below) — change it to another number instead. `PATCH /api/tasks/{id}` refuses (422) to complete `plan_patients` without a number.
  - `GET /api/practice-drugs/{practice_drug_id}/tasks` — returns `{drug_name, drug: {brand_name, codes, approval_date, storage_requirements, distributors (names), packages ([{ndc_11, strength_mg}])}, practice_drug: {id, status, planned_patients_per_month, hold_list_count, stock_on_hand, ready_at}, tasks[]}`. One call gives the workspace page everything it needs.
